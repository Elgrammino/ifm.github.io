## Задача приложения и аудитория

Это статическое устанавливаемое веб-приложение для посетителей форума 19–21 января 2027 года. Посетитель просматривает программу по дням и темам, открывает события и страницы спикеров, сохраняет события в личное расписание, ведёт и выгружает заметки, читает новости организаторов. Организатор меняет общую программу через редактор. Данные расписания и тексты сейчас предварительные; место, названия и участники требуют сверки перед настоящим запуском.

Визуальное направление согласовано с пользователем: сохранить и улучшить тёмный интерфейс, фотографию форума, золотой основной акцент, лаймовый и фиолетовый цвета из логотипа. `DESIGN.md` описывает токены, компоненты и границы. Логотип «МФИ 2027» уже лежит в `icon-*.png`; на заставке вокруг него вращается тонкое кольцо его цветов.

## Как устроены файлы

| Файл | Роль |
| --- | --- |
| `index.html` | Все экраны, стили, загрузка, навигация и редактор; это существующее приложение, не шаблон для замены. |
| `data.json` | Предварительные события, спикеры, ссылки и дилеры. На дату записи: 16 событий, 6 спикеров, 3 ссылки, 0 дилеров. |
| `storage.js` | Проверка и восстановление локальных данных, валидация состояния и событий, миграция старых локальных данных. |
| `remote.js` | Чтение Firebase Realtime Database, вход в Authentication и запись с ETag для разрешения конфликтов. |
| `firebase-config.js` | Публичные параметры веб-приложения Firebase; паролей здесь нет. Не копируй значения в журнал или переписку. |
| `database.rules.json` | Версия правил в рабочей копии. Это **не доказательство** того, что ровно те же правила опубликованы в Firebase Console. |
| `sw.js`, `manifest.json`, `icon-*.png` | Офлайн-кеш, установка PWA и иконки. При изменении кешируемых ресурсов поднимать версию кеша в `sw.js`. |
| `tests/regression.cjs`, `tests/remote.cjs` | Регрессионные проверки экранов, крайних данных, хранения, офлайна и удалённых правок. |
| `DESIGN.md`, `README.md` | Дизайн-система и обычное описание проекта; этот журнал добавляет историю и план продолжения. |

Личные заметки и избранное хранятся **на устройстве посетителя**, а не в Firebase. Общая программа хранится в Realtime Database в `/s`: сдвиг времени, отмены, добавленные события, новости. Приложение читает её при открытии, при возвращении на вкладку и примерно каждые 20 секунд. Если сеть пропала, показывает последнюю сохранённую программу; неудачная запись не объявляется опубликованной. Защита записи определяется **правилами на сервере Firebase**, а не скрытой кнопкой входа в интерфейсе.

Пользователь создал Firebase-проект `ifm-2027`, зарегистрировал веб-приложение, создал Realtime Database и подтвердил публикацию правил. Ранее пользователь проверил в двух сеансах, что общие изменения видны другому посетителю. Редактор новой версии открывается шестью нажатиями на карточку организатора; затем нужен вход Firebase Authentication с email и паролем. В источнике рабочей копии нет PIN. В файле правил рабочей копии разрешение на запись выдано одному UID. Пользователь позже спросил, как добавить второго организатора: нужно создать отдельную учётную запись в Authentication и добавить её UID в правило `.write`; неизвестно, сделал ли он это после разговора. ## Безопасность и оставшийся старый сайт

Новая проба и PR не содержат PIN: пароль организатора передаётся для входа в Firebase Authentication, а изменения записи контролирует Firebase Realtime Database по UID. Публичный Firebase web API key в конфиге — не пароль; его ограничения в Google Cloud нужно проверить, особенно потому, что пользователь при создании проекта включал Gemini. Для Gemini нужен отдельный ограниченный ключ; нельзя считать текущие ограничения проверенными по одному исходному коду.

**Корень `main` всё ещё показывает старое приложение.** В его опубликованном `index.html` есть встроенный PIN для старого демо-редактора, а адрес базы у старой версии пустой: правки остаются локальными. PIN не приводим здесь. Замена корня новым приложением в PR устраняет эту старую реализацию **только после слияния**; сейчас основной URL не стоит выдавать за актуальную пробу. Не сливай PR без согласования пользователя и проверки пробы на его телефоне.

Файл `database.rules.json` в рабочей копии закрывает запись на корневом уровне и разрешает запись в `/s` только авторизованному UID; опубликованное состояние Firebase Console и ограничения API key мы не читали. Если второй организатор добавлен вручную в консоли, файл правил в репозитории может отставать — синхронизировать после проверки, не публиковать предположение.
